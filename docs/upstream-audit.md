## 2. Complete Subsystem Audit of `openai/codex-plugin-cc` (`db52e28`)

`codex-plugin-cc` ships its plugin under `plugins/codex/` as zero-dependency ESM (`.mjs`) files checked with `tsc -p tsconfig.app-server.json` (`allowJs`, `checkJs`, `noEmit`) against types generated by `codex app-server generate-ts`. Below is the audit of all 17 upstream subsystems specified in `SPEC.md` Section 3.

### 2.1 Codex Companion Runtime (`plugins/codex/scripts/codex-companion.mjs`, 1,073 LOC)
- **Responsibilities**: CLI entrypoint supporting subcommands `setup`, `review`, `adversarial-review`, `task`, `task-worker`, `transfer`, `status`, `result`, `task-resume-candidate`, and `cancel`.
- **Observations**:
  - Clean orchestration logic for `executeReviewRun` and `executeTaskRun`, separating structured payload creation from human-readable markdown rendering.
  - **Claude Code coupling**: Reads `CODEX_COMPANION_SESSION_ID` (populated by Claude's `CLAUDE_ENV_FILE`), hardcodes `/codex:*` command hints in errors/output, hardcodes `STOP_REVIEW_TASK_MARKER = "Run a stop-gate review of the previous Claude turn."`, and defines `MODEL_ALIASES = new Map([["spark", "gpt-5.3-codex-spark"]])`.
  - **Stale protocol validation**: Line 71 hardcodes `VALID_REASONING_EFFORTS = new Set(["none", "minimal", "low", "medium", "high", "xhigh"])`, which **rejects `"max"` and `"ultra"`** supported by `gpt-6.2-sol` in `codex-cli 0.172.0`.
  - **Missing controls**: No per-job timeout (`timeout_seconds`), no maximum concurrent job cap, no pre-flight `model/list` validation.

### 2.2 App Server Client (`plugins/codex/scripts/lib/app-server.mjs`, 354 LOC)
- **Responsibilities**: Base JSON-RPC client (`AppServerClientBase`), direct child-process client (`SpawnedCodexAppServerClient`), and local-socket broker client (`BrokerCodexAppServerClient`), unified behind `CodexAppServerClient.connect(cwd, options)`.
- **Observations**:
  - **Clean core**: Line-buffered JSONL parsing, request ID correlation (`Map`), exit rejection propagation, notification routing, and `initialize` -> `initialized` handshake.
  - **Claude Code coupling**: Lines 19–30 read `../../.claude-plugin/plugin.json` and hardcode `DEFAULT_CLIENT_INFO = { title: "Codex Plugin", name: "Claude Code", version }`.
  - **Windows shell defect (DEP0190 & injection surface)**: Line 194 spawns `codex app-server` with `shell: process.platform === "win32" ? (process.env.SHELL || true) : false`. On Node 24 Windows, this triggers `[DEP0190]` deprecation warning, spawns an intermediate `cmd.exe` (or Git Bash if `SHELL` is set), and complicates clean process termination.
  - **Blind ServerRequest rejection**: Line 156 (`handleServerRequest`) replies `-32601 Unsupported server request` to ALL server-initiated RPCs (`item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, `item/permissions/requestApproval`, etc.). It cannot safely decline/cancel approval prompts or transition jobs to `awaiting_approval`.
  - **Unbounded buffers**: `this.lineBuffer` and `this.stderr` grow without cap.

### 2.3 App Server Broker (`app-server-broker.mjs` 252 LOC, `lib/broker-endpoint.mjs` 41 LOC, `lib/broker-lifecycle.mjs` 209 LOC)
- **Responsibilities**: Persistent detached Node process holding one `SpawnedCodexAppServerClient` and exposing a local Unix socket (`unix:<dir>/broker.sock`) or Windows named pipe (`pipe:\\.\pipe\<name>-codex-app-server`) to avoid cold-starting `codex app-server` on every CLI invocation.
- **Observations & Audit Findings**:
  - **Single-client exclusive lock**: Only one socket may own `activeRequestSocket` or `activeStreamSocket` at a time (lines 173–182). Concurrent requests receive `BROKER_BUSY_RPC_CODE (-32001)`, except `turn/interrupt` which is allowed through when no synchronous request is in flight. `codex.mjs` catches `-32001` and falls back to spawning a **direct** `codex app-server` process.
  - **Endpoint security gaps**:
    - `createBrokerSessionDir()` creates dirs in shared `os.tmpdir()` (`cxc-*`) without setting `0o700` dir / `0o600` socket permissions.
    - Windows named pipes (`\\.\pipe\<basename>-codex-app-server`) have no per-session authentication handshake or DACL hardening; any local process guessing the pipe name from `%TEMP%` can connect and send RPCs.
  - **Lifecycle gaps**:
    - Relies on Claude Code's `SessionEnd` hook to call `broker/shutdown` and clean up `broker.json`. Antigravity has **no `SessionEnd` hook**, so without an idle TTL and MCP-server shutdown cleanup, brokers would leak indefinitely.
    - `saveBrokerSession` uses non-atomic `fs.writeFileSync`.
    - `teardownBrokerSession` kills `existing.pid` without verifying process identity (PID reuse risk).
    - `waitForBrokerEndpoint` defaults to `2000ms`, which can be tight on cold Windows startup.

### 2.4 JSON-RPC Transport (`lib/app-server.mjs`)
- **Wire format**: Newline-delimited JSON (`JSON.stringify(msg) + "\n"`) over stdio (direct) or `net.Socket` (broker). Note that Codex App Server omits the `"jsonrpc": "2.0"` envelope field on the wire (standard `{ id, method, params }`, `{ id, result }`, `{ id, error }`, `{ method, params }`).
- **Notification suppression**: Handshake passes `optOutNotificationMethods: ["item/agentMessage/delta", "item/reasoning/summaryTextDelta", "item/reasoning/summaryPartAdded", "item/reasoning/textDelta"]` to avoid flooding the transport with per-token streaming deltas when only completed items are needed. This pattern is highly reusable.

### 2.5 Protocol Types (`lib/app-server-protocol.d.ts` 75 LOC, `tsconfig.app-server.json` 23 LOC)
- **Responsibilities**: Maps a curated subset of `codex app-server generate-ts` outputs (`initialize`, `externalAgentConfig/import`, `thread/start`, `thread/resume`, `thread/name/set`, `thread/list`, `review/start`, `turn/start`, `turn/interrupt`) into a strongly typed `AppServerMethodMap`.
- **Gap**: Does not declare `account/read`, `config/read`, `model/list`, `thread/read`, `windowsSandbox/readiness`, or approval `ServerRequest` payloads in `AppServerMethodMap` (upstream called `account/read` and `config/read` untyped or loosely typed). We will expand `AppServerMethodMap` directly against generated Codex `0.172.0` types.

### 2.6 Authentication & Readiness Checks (`lib/codex.mjs`, lines 758–958)
- **Responsibilities**: Checks `codex --version` + `codex app-server --help`, then connects to App Server and calls `account/read` (`{ refreshToken: false }`) and `config/read` (`{ includeLayers: false, cwd }`).
- **Strengths**:
  - Correctly supports ChatGPT login (`account.type === "chatgpt"`), API key (`account.type === "apiKey"`), and custom providers that do not require OpenAI auth (`requiresOpenaiAuth === false`, e.g., Ollama, LM Studio, or custom `model_providers`).
  - Never reads `~/.codex/auth.json` or any OAuth/API credentials directly.
  - Deliberately skips hard auth pre-flight on `task` execution so Codex itself can refresh an expired session token transparently (`tests/runtime.test.mjs:178`).
- **Gaps for `codex-plugin-agy`**:
  - Does not call `model/list` to check availability of `gpt-6.2-sol` or its supported reasoning efforts.
  - Passes `includeLayers: false` to `config/read`, missing project-trust diagnostics (`layers[].disabledReason` for untrusted `.codex/config.toml`).
  - Does not check `windowsSandbox/readiness` on Windows or verify broker health actively.

### 2.7 Job Management (`lib/state.mjs` 191 LOC, `lib/tracked-jobs.mjs` 204 LOC, `lib/job-control.mjs` 308 LOC)
- **Responsibilities**: Per-workspace state directory (`<stateRoot>/<slug>-<sha256_16>/`), `state.json` job index (capped at 50 jobs with automatic artifact pruning), per-job `jobs/<jobId>.json` and `jobs/<jobId>.log`, phase inference, elapsed/duration calculation, prefix-matching job lookup.
- **Audit Findings (Must Harden)**:
  1. **Claude env var**: `state.mjs:9` reads `CLAUDE_PLUGIN_DATA` (must switch to `PLUGIN_DATA` with safe user-scoped fallback, never world-readable `/tmp` if avoidable).
  2. **Non-atomic writes & race conditions**: `saveState` and `writeJobFile` use `fs.writeFileSync`; `updateState` performs unlocked read-modify-write. Concurrent workers writing simultaneously can corrupt `state.json` or lose job updates.
  3. **Limited state model**: Only tracks `queued`, `running`, `completed`, `failed`, `cancelled`. Missing `starting`, `awaiting_approval`, `cancelling`, `timed_out`, and `interrupted` required by `SPEC.md` Section 9.
  4. **No crash/stale-job reconciliation**: Dead worker PIDs stay marked `running` forever.
  5. **No log pagination/redaction**: `readJobProgressPreview` reads the entire log file into memory (`fs.readFileSync`) without size bounds or secret redaction.

### 2.8 Background Execution (`codex-companion.mjs`, lines 671–710 & 838–881)
- **Responsibilities**: Spawns detached `node codex-companion.mjs task-worker --cwd <cwd> --job-id <jobId>` with `detached: true, stdio: "ignore", windowsHide: true`, unrefs the child, and persists `{ status: "queued", pid, request }` to `<jobId>.json` and `state.json`.
- **Audit Findings**:
  - **Strength**: Detaching a worker process ensures background jobs survive short-lived MCP tool calls (and even MCP server restarts, provided the OS preserves the detached child process tree).
  - **Race bug**: In `enqueueBackgroundTask` (lines 688–698), `spawnDetachedTaskWorker` is called *before* `writeJobFile`! If the child starts faster than the parent writes `<jobId>.json`, `handleTaskWorker` throws `No stored job found for <jobId>`. We MUST write `<jobId>.json` atomically *before* spawning the worker!
  - **Review background mismatch**: Upstream `review` and `adversarial-review` only ran in the background via Claude Code's `Bash(..., run_in_background: true)` rather than via detached worker. In `codex-plugin-agy`, `codex_review` and `codex_adversarial_review` with `background: true` will use the same unified detached worker infrastructure as `codex_delegate`!

### 2.9 Session Persistence (`lib/codex.mjs`, `lib/state.mjs`)
- **Responsibilities**: Tasks pass `ephemeral: false` (`persistThread: true`) to `thread/start` and name threads `Codex Companion Task: <excerpt>` via `thread/name/set`, enabling `codex resume <threadId>`. Reviews pass `ephemeral: true`.
- **Gap**: Upstream does not persist a strict binding of `threadId -> { workspaceRoot, worktreePath, sandbox, approvalPolicy }` or verify via `thread/read` before resuming, which `SPEC.md` Section 7 ("确保 Thread 与对应 Workspace 及安全策略绑定") requires.

### 2.10 Thread Resume (`lib/codex.mjs:750, 1162`, `codex-companion.mjs:336, 928`)
- **Responsibilities**: Resumes via `thread/resume` (`{ threadId, cwd, model, approvalPolicy, sandbox }`), with fallback discovery via `thread/list` (`cwd`, `sortKey: "updated_at"`, `sourceKinds: ["appServer"]`, `searchTerm`).
- **Audit Note**: In Codex `0.172.0`, `ThreadResumeParams` supports `excludeTurns: true` to avoid deprecated full-history hydration on large threads, and `ThreadStartResponse` / `ThreadResumeResponse` return the effective `model`, `reasoningEffort`, `sandbox`, and `approvalPolicy`.

### 2.11 Task Cancellation (`codex-companion.mjs:963–1022`, `lib/codex.mjs:960–1000`, `lib/process.mjs:57–118`)
- **Responsibilities**: Calls `interruptAppServerTurn` (`turn/interrupt`) then `terminateProcessTree(job.pid)` (`taskkill /PID <pid> /T /F` on Windows, `kill(-pid, "SIGTERM")` on POSIX), then updates job state to `cancelled`.
- **Critical Audit Bugs**:
  1. **Direct-transport interrupt miss**: If the running job fell back from a busy broker to a **direct** `codex app-server` child inside the worker process, `interruptAppServerTurn` connects to the broker (or spawns a fresh app-server) which does NOT own that thread/turn, so `turn/interrupt` fails!
  2. **Unverified PID kill**: Kills stored `job.pid` without checking process identity (`startedAtMs` / command-line marker).
  3. **Completion race**: `runTrackedJob` does not check if the job transitioned to `cancelling`/`cancelled` before writing `completed`/`failed`, so the dying worker can overwrite `cancelled` back to `failed`.
  - **Fix in our architecture**: Each background worker handles a lightweight cancel signal (either broker `turn/interrupt` OR per-job IPC/control channel or cancel-marker file + verified-PID `SIGTERM` -> worker catches `SIGTERM`, calls `turn/interrupt` on its own live App Server client, waits briefly, exits cleanly; hard-kill only after grace period), with compare-and-set state transitions (`running -> cancelling -> cancelled`).

### 2.12 Review & Adversarial Review (`lib/git.mjs` 347 LOC, `lib/codex.mjs:1002–1056`, `prompts/adversarial-review.md`, `schemas/review-output.schema.json`)
- **Responsibilities**:
  - Normal Review: Uses `review/start` with `sandbox: "read-only"` and native `ReviewTarget` (`uncommittedChanges` or `baseBranch`).
  - Adversarial Review: Uses `lib/git.mjs` (`collectReviewContext` — inline diff for `<= 2` files & `<= 256 KiB`, else lightweight summary instructing Codex to self-collect via read-only git commands) + `prompts/adversarial-review.md` + `turn/start` with `sandbox: "read-only"` and `outputSchema: schemas/review-output.schema.json`.
- **Strengths**:
  - Commit `db52e28` (#447) explicitly hardened `lib/git.mjs` to pass `shell: false` on all `git` invocations!
  - `prompts/adversarial-review.md` and `schemas/review-output.schema.json` are battle-tested and host-agnostic.
- **Gaps for `SPEC.md` Section 7**:
  - Upstream `review` only exposes `uncommittedChanges` and `baseBranch`, ignoring Codex `0.172.0`'s native `commit` (`{ type: "commit", sha, title }`) and `custom` (`{ type: "custom", instructions }`) `ReviewTarget` variants, and does not support staged-only or path-filtered review scopes.
  - `lib/git.mjs` passes `baseRef` directly to `git merge-base HEAD <baseRef>` without rejecting refs starting with `-` (git option-injection risk) or validating path filters against traversal.

### 2.13 Session Transfer (`lib/claude-session-transfer.mjs` 44 LOC, `lib/codex.mjs:653–730, 1058–1093`)
- **Responsibilities**: Validates a `.jsonl` path strictly under `~/.claude/projects`, calls `externalAgentConfig/import` with `itemType: "SESSIONS"`, awaits `externalAgentConfig/import/completed`, and reads `$CODEX_HOME/external_agent_session_imports.json` matching `realpath` + SHA-256 to recover `imported_thread_id`.
- **Antigravity Verification**:
  - Codex's `externalAgentConfig/import` expects Claude Code session JSONL format (`~/.claude/projects/...`). It has **no documented Antigravity transcript importer**.
  - Although Antigravity passes `transcriptPath` to hooks, `SPEC.md` Section 7 explicitly prohibits reverse-engineering private Antigravity databases/chats and specifies **Neon's explicit Structured Handoff Package** when no official cross-agent transcript importer exists.
  - Therefore `claude-session-transfer.mjs` and `externalAgentConfig/import` are **Unsupported / Replaced** by a structured handoff transfer implementation (`codex_transfer`) that starts a persistent Codex thread (`ephemeral: false`) seeded with Neon's structured handoff package and returns `threadId` + `codex resume <threadId>`.

### 2.14 Stop Gate / Review Gate (`stop-review-gate-hook.mjs` 184 LOC, `prompts/stop-review-gate.md` 36 LOC, `hooks/hooks.json` 38 LOC)
- **Responsibilities**: On Claude `Stop`, if `config.stopReviewGate === true`, spawns `codex-companion.mjs task --json <stop-review-gate prompt>` (15m timeout), parses first line `ALLOW:` or `BLOCK:`, and outputs `{"decision": "block", "reason": "..."}` to stdout.
- **Audit Findings**:
  - **No recursion cap**: Upstream `stop-review-gate-hook.mjs` has no max-runs counter and no env recursion guard (relying solely on the prompt's instruction to `ALLOW` non-edit turns), which `README.md` itself warns can create infinite loops!
  - **Incompatible hook contract**: Claude Code uses `{ "hooks": { "Stop": [{ "hooks": [...] }] } }`, snake_case input (`session_id`, `last_assistant_message`), and `{"decision": "block"}`. Antigravity uses named top-level hook groups, flat `Stop` arrays, camelCase input (`conversationId`, `continuationActive`, `executionNum`, `terminationReason`, `fullyIdle`, `lastUserInput`), and `{"decision": "continue", "reason": "..."}`!

### 2.15 Error Handling (`lib/codex.mjs`, `lib/app-server.mjs`, `lib/process.mjs`)
- **Observations**:
  - Propagates JSON-RPC error codes (`rpcCode`) and cleaned stderr (`cleanCodexStderr`).
  - Handles multi-agent subagent turn inference (`scheduleInferredCompletion` 250ms debounce after `final_answer` when `pendingCollaborations` and `activeSubagentTurns` drain — very valuable upstream edge-case handling to preserve!).
  - **Gaps**: Does not map `TurnError.codexErrorInfo` (`modelNotFound`, `unauthorized`, `rateLimitExceeded`, `usageLimitExceeded`, `contextWindowExceeded`, `sandboxError`, etc.) into structured machine-readable error codes for MCP consumers, and does not redact secrets from error messages or stderr.

### 2.16 Result Delivery (`lib/render.mjs` 465 LOC, `skills/codex-result-handling/SKILL.md` 21 LOC)
- **Responsibilities**: Formats setup, status, review, adversarial review, task, stored result, and cancel reports into Markdown; `codex-result-handling` enforces strict verbatim/evidence-boundary presentation and forbids auto-applying review fixes.
- **Adaptation**: In `codex-plugin-agy`, MCP tools return **compact, structured JSON** (both `content` JSON text and `structuredContent`) with strict separation between `pluginMeta` and `workerOutput`, bounded/paginated diffs and logs, and optional human-readable summary rendering — while preserving the evidence-boundary and no-auto-fix principles from `codex-result-handling`.

### 2.17 Claude Code-Specific Integration
- `.claude-plugin/plugin.json` & `.claude-plugin/marketplace.json`: Replaced by Antigravity `plugin.json` (`https://antigravity.google/schemas/v1/plugin.json`).
- `commands/*.md` (8 slash commands with Claude-only `!` shell bang syntax, `$ARGUMENTS`, `allowed-tools`, `AskUserQuestion`, `Bash(..., run_in_background: true)`): Replaced by Antigravity `skills/<name>/SKILL.md` + MCP tools.

- `skills/gpt-5-4-prompting/`: Model-specific prompting guide for GPT-5.4 inside `codex-rescue`. Its structural XML prompt-contract principles (`<task>`, `<verification_loop>`, `<grounding_rules>`, `<action_safety>`) are selectively adapted into our `codex-orchestrator` skill for GPT-6.2 Sol task delegation prompts without carrying over GPT-5.4-specific claims.

### 3.2 Critical Protocol Divergences Found vs `codex-plugin-cc` (`v1.0.6`)

1. **`ReasoningEffort` is open-ended and `gpt-6.2-sol` supports `max` and `ultra`**:
   - Generated `ReasoningEffort.ts` is `export type ReasoningEffort = string;`.
   - Live `model/list` on `codex-cli 0.172.0` confirmed `gpt-6.2-sol` supports `["low", "medium", "high", "xhigh", "max", "ultra"]` (with `defaultReasoningEffort: "low"`, `isDefault: true`), and does **not** list `"none"` or `"minimal"`.
   - **Design mandate**: Validate requested `(model, reasoning_effort)` dynamically against `model/list` rather than upstream's hardcoded 6-value set.
2. **`ReviewDelivery` is strictly `"inline"` in `0.172.0`**:
   - Generated `ReviewDelivery.ts` is `export type ReviewDelivery = "inline";` (`"detached"` has been removed from the v2 protocol).
3. **`ReviewTarget` natively supports 4 variants**:
   - `{ type: "uncommittedChanges" }`, `{ type: "baseBranch", branch }`, `{ type: "commit", sha, title }`, `{ type: "custom", instructions }`.
   - `codex_review` can now support uncommitted, base branch, commit SHA, and custom instructions natively via `review/start`, falling back to read-only `turn/start` only when staged-only or path-filtered diff scoping is requested (or for structured JSON `codex_adversarial_review`).
4. **Rich Server Notifications available in `0.172.0` (unused by upstream)**:
   - `thread/tokenUsage/updated` -> `{ threadId, turnId, tokenUsage: { total, last, modelContextWindow } }` (`totalTokens`, `inputTokens`, `cachedInputTokens`, `cacheWriteInputTokens`, `outputTokens`, `reasoningOutputTokens`).
   - `turn/diff/updated` -> `{ threadId, turnId, diff }` (aggregated turn-level unified diff).
   - `model/rerouted` -> `{ threadId, turnId, fromModel, toModel, reason }` (must be surfaced transparently so silent model reroutes are never hidden).
   - `item/completed` for `commandExecution` includes `command`, `cwd`, `status`, `exitCode`, `durationMs`, `aggregatedOutput` — enables real `commandsExecuted` and test execution summaries without guessing.
5. **Typed Approval Server Requests (`ServerRequest.ts`)**:
   - `item/commandExecution/requestApproval` -> `{ decision: "accept" | "acceptForSession" | "decline" | "cancel" | ... }`
   - `item/fileChange/requestApproval` -> `{ decision: "accept" | "acceptForSession" | "decline" | "cancel" }`
   - `item/permissions/requestApproval` -> `{ permissions: GrantedPermissionProfile, scope: PermissionGrantScope }`
   - `item/tool/requestUserInput`, `mcpServer/elicitation/request`, legacy `execCommandApproval`, `applyPatchApproval`.
   - In non-interactive MCP mode, our client MUST NEVER send `"accept"`; it responds fail-closed (`"cancel"` or `"decline"` / empty `{}` permission grant) and transitions the job to `awaiting_approval` with `codex resume <threadId>` guidance.
6. **Codex `SandboxPolicy` vs `allowed_paths`**:
   - `SandboxPolicy.workspaceWrite` (`{ type: "workspaceWrite", writableRoots, networkAccess, excludeTmpdirEnvVar, excludeSlashTmp }`) operates at directory-root granularity and always permits writes under `cwd`.
   - Therefore, file-level `allowed_paths` in `codex_delegate` **cannot** be enforced as an OS-level sandbox boundary by Codex App Server; it MUST be documented and typed as a **task-scope prompt constraint + post-run diff audit warning**, NOT a security sandbox boundary (`SPEC.md` line 416).
7. **Codex App Server Daemon (`codex app-server daemon`)**:
   - `codex 0.172.0` includes an experimental `codex app-server daemon` and `--listen unix://` / `ws://`. Because `codex app-server` itself is marked experimental and its shared daemon is tied to user CLI/TUI sessions (with potential lifecycle conflicts), `codex-plugin-agy` retains a plugin-owned isolated broker + direct-client fallback architecture (reusing and hardening upstream's design) while keeping transport pluggable for future official daemon adoption.

## 4. Verified Google Antigravity Plugin Specification Audit

Verified against `https://antigravity.google/schemas/v1/plugin.json`, `build-plugins.md`, `plugins.md`, `mcp.md`, `skills.md`, `rules.md`, `hooks.md`, `customization-discovery.md`, `subagents.md`, `permissions.md`, built-in Antigravity skills, and empirical testing with local `agy 1.1.27`.

### 4.1 Manifest (`plugin.json`) Contract
- Location: `<plugin-root>/plugin.json` (or `.antigravity-plugin/plugin.json` in multi-provider repos).
- Strict JSON Schema (`https://antigravity.google/schemas/v1/plugin.json`):
  - `additionalProperties: false` (unknown keys are ignored at runtime and flagged by `agy plugin validate`).
  - `required: ["name"]`.
  - `name`: lowercase `kebab-case` (`^[a-z0-9]+(-[a-z0-9]+)*$` recommended for `--strict` & Marketplace; schema allows `^[a-zA-Z0-9_-]+$`). Must NOT lead with `"Antigravity"`, `"Gemini"`, `"Claude"`, or `"Cursor"`.
  - `displayName`: human-readable title; omit suffixes like `"Plugin"` or `"MCP"` and avoid host prefixes (e.g., `"Codex Worker"`).
  - `description`, `version` (SemVer), `logo` (relative `.svg`/`.png`/`.jpg`/`.jpeg`/`.webp`, 1:1 square `>=128x128` with ~10% transparent margin), `suggestedPrompts` (max 3 non-empty strings), `author` (string or `{ name, email?, url? }`), `homepage` (`https://`), `repository` (**strictly `type: "string"`** in live schema v1 — NOT an object!), `license` (`"Apache-2.0"`), `keywords` (`string[]`), `disabled` (default `false`), `skills`, `extensions`.

### 4.2 Path Variables & Runtime Environment
- `${PLUGIN_ROOT}` and `${PLUGIN_DATA}` are **officially supported** in `<plugin-root>/mcp_config.json` (`args`, `cwd`, custom `env`) and automatically exported as `PLUGIN_ROOT` and `PLUGIN_DATA` environment variables in both MCP server processes and command hooks (`hooks.json`).
- **Critical `hooks.json` rule**: Antigravity does **NOT** expand `${PLUGIN_ROOT}` inside `hooks.json` `command` strings! Hooks execute with `cwd = <plugin-root>` via `sh -c` (POSIX) or `cmd /c` (Windows). Commands MUST use relative script paths (e.g., `node ./scripts/hooks.mjs ...`) and read `process.env.PLUGIN_ROOT` / `process.env.PLUGIN_DATA` inside Node.js for full cross-platform portability.

### 4.3 MCP Server Integration (`mcp_config.json`)
- Schema: `{ "mcpServers": { "<server-key>": { "command": "node", "args": [...], "env"?: {...}, "cwd"?: "...", "timeoutSeconds"?: <int>, "tools"?: { "<toolName>": { "eager": true, "background"?: "off" | "always" } } } } }`.
- Server key namespacing: `<plugin-name>_<server-key>` globally (use concise plugin-scoped key like `"codex"` so namespace is `codex-plugin-agy_codex`).
- Timeouts: Default 300s connect, 180s per tool call. Setting `timeoutSeconds` (e.g., `600`) updates both limits; `-1` disables both. Since foreground tasks/reviews may exceed 180s, set a sensible `timeoutSeconds` (e.g., `600`) AND recommend `background: true` for long-running work.
- Tool loading: All MCP tools are **lazy-loaded by default** (cached to `<app-data-dir>/mcp/<serverName>/<toolName>.json` and invoked via `call_mcp_tool`). Marking high-frequency core tools (`codex_delegate`, `codex_status`, `codex_result`) as `"eager": true` enables single-turn direct invocation while keeping secondary tools lazy to minimize per-turn context tokens.
- Permissions: Unconfigured MCP tools default to **Ask** (`mcp(server/tool)`, `mcp(server/*)`). Plugin installation does NOT bypass Antigravity's permission engine.
- **No automatic `npm install`**: Installed plugins unpack into read-only `~/.gemini/config/plugins/<name>/`. Release/Marketplace packages MUST ship a self-contained bundled runtime (`esbuild`) requiring zero `node_modules`.

### 4.4 Skills, Rules, Subagents & Hooks
- **Skills (`skills/<name>/SKILL.md`)**: YAML frontmatter requires `name` (must match parent directory name) and `description`; optional `disable-model-invocation: true`. Automatically exposed as `/<name>` slash commands in App, CLI, and IDE (namespaced `<plugin>:<name>` to prevent collisions).
- **Rules (`rules/AGENTS.md` and `rules/<name>.md`)**:
  - `rules/AGENTS.md` (no frontmatter) is always-on while the plugin is enabled.
  - `rules/<name>.md` requires YAML frontmatter with `trigger`: `always_on | model_decision | glob | manual` (`globs` must be a comma-separated string, NOT a YAML array).
  - Size limits: 24 KB per file, 20,000-token aggregate rules budget.
  - Root `AGENTS.md` is ignored by the plugin loader (safe for contributor/agent development docs; newer `agy` versions emit a multi-tool warning which CI filters per `build-plugins.md`).
- **Hooks (`hooks.json`)**:
  - Supported events: `SessionStart`, `PreToolUse`, `PostToolUse`, `PreInvocation`, `PostInvocation`, `Stop`.
  - **NOT supported**: `SessionEnd` (no host hook fires on session close).
  - Format: top-level named hook groups with optional `"enabled": false`; `SessionStart` and `Stop` use **flat handler arrays** (no `matcher` wrapper).
  - Payloads: camelCase JSON on stdin (`conversationId`, `workspacePaths`, `transcriptPath`, `artifactDirectoryPath`, `modelName`, `lastUserInput`, `hookEventName`, `cwd`; plus on `Stop`: `executionNum`, `terminationReason`, `error`, `fullyIdle`, `continuationActive`).
  - `Stop` stdout contract: `{"decision": "continue", "reason": "..."}` blocks stopping; `{}` allows stopping; non-zero exit fails open.
- **Empirical `agy 1.1.27` CLI Validation Note**:
  - On local `agy 1.1.27`, `agy plugin validate <path>` requires `<path>` as the **first positional argument** (putting `--strict` or `--json` *before* `<path>` fails with `GetFileAttributesEx --json\plugin.json`, whereas newer CLI releases documented online accept `--strict`/`--json` flags). Build scripts and CI must document and handle both CLI versions cleanly.
